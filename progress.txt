2. **Added `resolveDependenciesMaven` private method in `Lib.scala`**:
   - Takes the worker, deps, force, repositories, sources, mapDependencies, ctx, boms
   - Converts all Coursier types → worker types using the helpers above
   - Calls `worker.resolveClasspath(...)` and wraps results as `Seq[PathRef]`
   - Catches exceptions and returns `Result.Failure` with `[maven-resolver]` prefix

3. **Added dispatch logic in `Lib.resolveDependencies`**:
   - New `@unroll mavenResolverWorker: Option[MavenResolverSupport.Api] = None` parameter (binary compatible)
   - Pattern match on `(ResolverType.current, mavenResolverWorker)`:
     - `(Maven, Some(worker))` → delegates to `resolveDependenciesMaven`
     - `_` (default/Coursier) → existing Coursier path via `Jvm.resolveDependencies` (zero logic change)

4. **Added `mavenResolverWorker` parameter to `CoursierModule.Resolver`**:
   - New `@unroll mavenResolverWorker: Option[MavenResolverSupport.Api] = None` (binary compatible)
   - `Resolver.classpath` passes it through to `Lib.resolveDependencies`

5. **Wired worker in `CoursierModule.millResolver` and `defaultResolver`**:
   - **Key design decision**: The `ResolverType.current` check happens OUTSIDE the `Task.Anon` macro body. This is critical because Mill's `Task.Anon` macro eagerly extracts ALL task references from the body (even inside `if` conditionals), which would cause `mavenResolverWorker()` to be evaluated even for Coursier backend.
   - Split into two `Task.Anon` branches: one for Maven (references `mavenResolverWorker()`) and one for Coursier (no worker reference).

6. **Initialized worker in `MavenResolverSupport.mavenResolverWorker` task**:
   - After reflective construction, calls `worker.initialize(SessionConfig(...))` with default `~/.m2/repository` path
   - Worker is ready to use immediately after task evaluation

### Design decisions:
- **Dispatch in `Lib`, not `Jvm`**: The `Jvm.scala` module (in `libs/util`) cannot import `MavenResolverSupport.Api` (from `libs/javalib`) due to module dependency constraints. `Lib.scala` (in `libs/javalib`) is the natural integration layer with access to both type systems. Zero changes to `Jvm.scala`.
- **Task macro workaround**: Mill's `Task.Anon` macro traverses the entire AST and extracts all `someTask()` references as dependencies, even inside runtime conditionals. To avoid eagerly evaluating `mavenResolverWorker()` for Coursier backend, we check `ResolverType.current` outside the macro boundary, using two separate `Task.Anon` blocks.

## TICKET-012: resolveMetadata + Resolution construction adapter

**Status:** Complete
**Date:** 2026-04-09

### What was done:
1. **Implemented `resolveMetadata` in `MavenResolverWorkerImpl`**:
   - Refactored `resolveCommon` to extract `buildCollectRequest` method (shared with `resolveMetadata`)
   - `resolveMetadata` resolves dependencies, then walks the `DependencyNode` tree to build:
     - `transitiveDeps: Map[String, Seq[ResolvedDep]]` — each dep mapped to its direct children in the tree
     - `orderedDeps: Seq[ResolvedDep]` — DFS traversal of all resolved deps
     - `projectCache: Map[String, ProjectInfo]` — POM metadata for each resolved dep
   - Tree walking via `buildTransitiveDeps`, `buildOrderedDeps`, `buildProjectCache` helper methods
   - For `projectCache`, reads POM metadata via two mechanisms:
     - `ArtifactDescriptorRequest` for dependency management overrides (effective POM, includes parent merging)
     - Direct POM file XML parsing for licenses and parent info (JDK DOM API with XXE protection disabled)
   - POM parsing uses `directChild`/`directChildren` to avoid false matches from nested elements
   - All exceptions wrapped with `[maven-resolver]` prefix per design convention

2. **Added `toResolution` method to `CoursierTypeAdapter`**:

       - `info.licenseInfo`: `Seq[Info.License]` from POM licenses
       - `parent0`: `Option[(Module, Version)]` from POM parent
       - `configurations`: standard Maven scope mapping (compile, runtime, provided)
       - `dependencies0`: direct children from `transitiveDeps`
     - `rootDependencies`: original Coursier deps (for orderedDependencies computation)
     - `dependencySet`: all resolved deps (for `dependencies`, `minDependencies`)
   - Uses dep cache (`depCache`) to ensure Coursier `Dependency` objects are reused as both keys and values
   - Root deps registered in cache first so `finalDependenciesCache` keys match caller lookup deps
   - `NoopArtifactSource` for project cache (Maven resolution already resolved artifacts)

3. **Added backend switch to `Lib.resolveDependenciesMetadataSafe`**:
   - New `@unroll mavenResolverWorker: Option[MavenResolverSupport.Api] = None` parameter (binary compatible)

### Key design decisions:
- **`transitiveDeps` semantics**: Maps each dep to its DIRECT children (not all transitives). This matches Coursier's `finalDependenciesCache` semantics where `dependenciesOf0(dep)` returns direct dependencies, enabling correct recursive tree walking by `orderedDependencies` and `renderDepsTree`.

- **Dep management overrides**: Uses `ArtifactDescriptorRequest` which reads the effective POM (including parent merging), so overrides include inherited dependency management.
- **`@unroll` on new parameter**: Binary compatible with existing callers that don't pass `mavenResolverWorker`.

     - `runProducesOutput` — verifies `foo.run` outputs `["hello","maven-resolver"]`
     - `invalidBackendValue` — adds `//| mill-resolver-backend: invalid` header, verifies launcher fails with "Valid values" error

2. **Fixed `defaultResolver` circular dependency in `CoursierModule.scala`**:
   - `defaultResolver` now always uses Coursier (never Maven), because it resolves Mill's own internal modules (workers, plugins). Using Maven here would create a circular dependency: `defaultResolver` → `mavenResolverWorker` → `mavenResolverWorkerClasspath` → `defaultResolver`
   - Only `millResolver` dispatches to the configured backend for user dependency resolution

3. **Fixed `mill-internal` synthetic dep handling in `JavaModule.scala`**:
   - `resolvedMvnDeps0`: when Maven backend is active, passes actual Maven deps (`mandatoryMvnDeps`, `mvnDeps`, `compileMvnDeps`) directly instead of `mill-internal` synthetic Coursier deps
   - `resolvedRunMvnDeps`: same pattern — passes `mandatoryMvnDeps`, `mvnDeps`, `runMvnDeps` directly for Maven
   - The `mill-internal` synthetic deps (organization=`mill-internal`, version=`0+mill-internal`) are Coursier constructs for project-based resolution and are not real Maven artifacts

4. **Test module auto-discovered** — `Cross[IntegrationCrossModule](build.listCross)` automatically picks up the `maven-resolver` directory under `integration/feature/`

### Design decisions:
- **No `.mill-jvm-opts` for tests**: Setting `mill.resolver.backend=maven` via `.mill-jvm-opts` causes daemon restart issues in the shared-output integration test mode (`NoClassDefFoundError` for Coursier classloader dependencies during daemon lifecycle). The Maven resolver worker is already covered by 17 unit tests (`libs.javalib.maven-resolver-worker.test`) and 20 core engine tests (`libs.javalib.maven-resolver-core.test`).
- **`defaultResolver` always uses Coursier**: Mill's internal module resolution (workers, plugins, JVM worker classpath) must use Coursier regardless of the configured backend. This is necessary because: (a) the Maven resolver worker is loaded via `defaultResolver`, creating a circular dependency, and (b) Mill's internal SNAPSHOT modules are only available via `COURSIER_REPOSITORIES` local repos, not Maven Central.
- **Direct deps for Maven path**: When `ResolverType.current == Maven`, `resolvedMvnDeps0` passes the actual Maven deps directly rather than the synthetic `mill-internal` root dep. This works because the Maven resolver resolves transitives from the actual dependency coordinates, unlike Coursier which uses project-based resolution with synthetic root deps.
- **CI job deferred**: The CI configuration aspect of ticket 014 is deferred — the integration test runs as part of the standard `integration.feature` CI job via selective execution.

### Known limitations:
- **Multi-module Maven resolution**: When a module has `moduleDeps`, the Maven path resolves each module's external Maven deps independently. Transitive Maven deps from module deps may be resolved separately per-module rather than in a single resolution tree. This matches the runtime behavior since `transitiveCompileClasspath` assembles the full classpath from per-module resolved deps.
